# 05. 기술 검토 노트

작성: 길선영 · 2026-10-29 ~ 2026-11-15

프로젝트를 진행하며 조사하고 팀에서 결정한 기술적 질문들을 정리한다.

## 1. 하드웨어 단말이 왜 필요한가

스마트폰에도 가속도계, 자이로, GPS가 있으므로 "폰이 있는데 왜 따로 장치를 다는가"라는 질문에 답하기 위해 정리했다.

| 근거 | 설명 |
|---|---|
| 카메라는 "보고", IMU는 "느낀다" | depth 카메라를 빼면서 위험이 얼마나 심한지 잴 수단이 없어졌다. 프레임에 고정한 IMU는 바퀴가 받은 충격 크기를 직접 재므로 **심각도** 측정을 맡는다. |
| 카메라가 못 보는 위험을 잡는다 | 밤, 비, 역광, 그림자, 물에 가려진 포트홀, 눈에 잘 안 띄는 단차는 카메라가 놓치기 쉽다. IMU는 환경과 상관없이 충격으로 잡는다. |
| 폰 센서로는 충격을 정확히 재기 어렵다 | 폰은 거치대의 고무 패드 때문에 충격이 흡수되거나 흔들림이 더해진다. 폰 센서는 읽는 간격이 일정하지 않고, 카메라·AI 처리로 이미 부하가 크다. |
| 폰 없이도 데이터를 모을 수 있다 | 단말만 달면 폰을 거치하지 않은 자전거도 노면 데이터를 쌓을 수 있다. |

**GPS의 역할:** GPS는 폰과 겹친다. 폰과 연결됐을 때는 폰 GPS를 쓰고, 단말 GPS는 폰 없이 단독으로 기록할 때 위치를 남기는 용도로 정한다.

**증명 실험(제안):** 같은 자전거에 폰(거치대)과 단말(프레임 고정)을 함께 달고 같은 요철을 여러 번 지나간 뒤 두 충격 그래프를 겹쳐 비교한다.

> 한 줄 요약: 스마트폰 카메라가 위험을 **찾고**, 프레임에 고정한 IMU가 위험이 **얼마나 심한지 잰다.**

## 2. "depth를 2D로 전환"의 의미

- **depth 카메라:** 화면 속 각 지점까지의 거리(깊이)를 재는 특수 카메라. 땅이 얼마나 패였는지 측정할 수 있지만 비싸고, 처리용 컴퓨터가 따로 필요하다.
- **2D(일반) 카메라:** 스마트폰처럼 평범한 영상만 찍는다. 거리는 직접 못 재지만, AI가 영상을 보고 위험 요소를 알아볼 수 있다.

해석은 두 가지가 가능하다.

1. depth 카메라를 빼고 일반 카메라로 위험을 인식한다. (현재 진행 방향)
2. 일반 카메라 영상에서 AI로 깊이를 추정한다(예: Depth Anything). 

어느 쪽이든 depth 카메라 장비는 필요 없다. 카메라에서 위험까지의 거리는 **지면 보정표**(폰 앞 2, 4, 6, 8, 10, 15m에 표시를 두고 화면 세로 위치와 실제 거리를 대응)로 구할 수 있다.

## 3. 노트북 카메라로 객체 인식 확인

팀원 제안: 앱을 만들기 전에 노트북 카메라로 간단한 화면을 만들어 객체 인식이 되는지만 먼저 확인한다. 교수님이 제안하신 "일반 카메라로 위험 인식" 방향이 실제로 되는지 가장 싸고 빠르게 검증하는 단계다.

| 용어 | 설명 |
|---|---|
| YOLO | 사진에서 "무엇이, 어디에" 있는지 한 번에 찾는 AI 모델. 새로 학습시키기 쉽다. YOLOv8n의 n은 nano(가장 작은 크기)로 스마트폰에서도 빠르게 돈다. |
| COCO-SSD | 일상 물체 80종을 이미 학습한 모델. 웹에서 바로 쓸 수 있지만 포트홀은 모른다. |
| COCO | 일상 물체 80종 사진 데이터셋 이름 |

**순서:** 기본 YOLO로 사람·컵 인식 확인 → 포트홀 사진을 비춰 기본 모델이 모른다는 것 확인 → 포트홀 데이터셋으로 학습 → 학습한 모델(best.pt)로 다시 확인.

## 4. 라즈베리파이가 필요한 경우

| | ESP32 | 라즈베리파이 |
|---|---|---|
| 정체 | 작은 제어용 칩 | 작은 컴퓨터 |
| 잘하는 일 | 센서 값 읽기, 저장, 전송 | 영상 처리, AI 모델 실행 |
| YOLO 실행 | 불가 | 가능 |
| 전력 | 아주 적음 | 많음 |

라즈베리파이는 카메라 영상을 자전거 장치에서 직접 처리하거나 depth 카메라를 쓸 때 필요하다. 현재는 스마트폰이 카메라와 AI를 맡으므로 **필요 없다.** 스마트폰 처리 속도가 목표에 크게 못 미칠 때만 대안으로 검토한다.

## 5. 앱 개발 방식: 웹 vs 앱

| 기능 | 반응형 웹 | 안드로이드 앱 |
|---|---|---|
| 지도, 제보, 조회 | 충분 | 충분 |
| 위치 추적, 음성 알림 | 화면이 켜져 있을 때만 | 화면이 꺼져도 가능 |
| 진동 알림 | 아이폰 미지원 | 가능 |
| 단말 BLE 연결 | 아이폰 미지원 | 가능 |
| 카메라 AI 속도 | 느릴 수 있음 | 더 빠름 (TFLite) |

**결정:** Flutter로 앱을 만든다. 코드 하나로 안드로이드와 아이폰 앱을 함께 만들 수 있다. Flutter는 JS가 아니라 Dart 언어를 쓰지만 문법이 비슷하다.

| 기능 | Flutter 패키지 |
|---|---|
| 지도 (OpenStreetMap) | flutter_map |
| 위치 추적 | geolocator |
| 음성 알림 | flutter_tts |
| 진동 | vibration |
| 화면 켜짐 유지 | wakelock_plus |
| 단말 BLE 연결 | flutter_blue_plus |
| 카메라 AI | camera + tflite_flutter |
| 서버 통신 | http 또는 dio |

## 6. 지도 표시 디자인 검토

- **색은 위험도 하나만 표현한다.** 확정·미확인은 색이 아니라 테두리나 투명도로 구분한다. 색 단계는 3단계(노랑·주황·빨강)가 구분하기 쉽다.
- **줌 단계별 표현:** 멀리서는 숫자 묶음(클러스터), 가까이서는 개별 마커와 아이콘.
- **종류는 필터 칩으로** 골라서 본다.
- **도로 구간 색칠**은 맵 매칭이 필요해 어려우므로 향후 확장으로 둔다.

이 표시를 위해 서버가 위험 지점마다 보내야 하는 값: 유형, 위험도, 확정 여부, 제보·감지 횟수, 최근 갱신 시각. 위험도 계산은 모든 사용자에게 같은 색이 나오도록 서버에서 한다.

## 7. 데이터·서버 연동 파트 (담당: 길선영)

앱과 서버 사이에서 데이터를 주고받는 역할이다.

1. **실제 서버 연결:** 가짜 데이터를 서버의 위험 목록으로 교체한다.
2. **제보 전송:** 제보 화면의 유형·사진·설명·위치를 서버로 보내고, 확인 응답을 전송한다.
3. **위험 지점 새로고침:** 30초마다 또는 300m 이동 시 주변 위험 목록을 다시 받는다.
4. **네트워크 끊김·오류 처리:** 끊기면 마지막 목록을 유지하고 다시 시도하며, 실패한 제보는 저장했다가 연결 시 다시 보낸다.

서버 담당과 먼저 정할 것: 서버 주소, API 주소와 필드 이름, 사진 전송 방식, 지도 색 표시에 필요한 값. 현재 확정된 형식은 [`docs/api.md`](../api.md)를 따른다.

## 8. 협업 방식

- 코드는 GitHub 저장소 하나에서 관리하고, 각자 자기 폴더만 수정한다.
- AI로 코드를 작성할 때는 팀 규칙(폴더 구조, 담당자, API 형식, 사용 패키지)을 함께 제공해 모두 같은 규칙으로 코드를 만든다.
- 기능 하나씩 작게 만들고, 실제 폰에서 실행해 확인한 뒤 올린다.
- 각자 맡은 코드는 직접 설명할 수 있을 만큼 이해한다.
- 매주 1회 전원이 최신 코드로 전체 흐름을 실행해 본다.
