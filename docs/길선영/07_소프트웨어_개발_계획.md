# 소프트웨어 파트 개발 계획

노면 위험 감지 프로젝트 · 처음부터 개발 기준 · 이번 학기(11~16주차) 및 겨울방학 계획 · 기준일 2026-11-15

> 참고: 이 문서의 API 초안(필드 이름 `lng`, `timestamp` 등)은 계획 당시 초안이다. 현재 팀 기준은 저장소의 [`docs/api.md`](../api.md)이며, 필드 이름은 `lon`, `time`, `event_id`로 확정되었다.

## 1. 전제와 목표

#### 전제

- 소프트웨어 팀 3명이 앱(Flutter)과 서버를 처음부터 새로 만든다.

- 하드웨어 팀(단말, 카메라 AI 모델)과는 **서버를 가운데 두고** 연결한다. 코드를 직접 합치지 않고, 약속한 데이터 형식으로만 주고받는다.

- 서버를 맡을 사람이 따로 없다면 **데이터·서버 파트가 서버까지 만든다.** (팀 확인 필요)

> **이번 학기 목표 (16주차까지)**
> 단말이 감지한 충격과 카메라가 인식한 위험이 서버에 저장되고, 앱 지도에 표시되며, 실제 주행 중 위험 지점에 가까워지면 음성으로 알린다.

#### 겨울방학으로 넘기는 것

- 앱 안에 카메라 AI 넣기 (이번 학기는 카메라 AI 담당이 노트북·DroidCam으로 인식하고 결과만 서버로 보냄)

- 화면이 꺼져도 알림(백그라운드), 단말 블루투스 연결

- 필터, 신뢰도 계산 고도화, 오래된 위험 자동 만료

## 2. 만들 것 전체 그림

```text
[단말 ESP32]  ---충격 이벤트(와이파이)--->  [서버 + DB]
[카메라 AI]   ---인식 결과-------------->  [서버 + DB]
[Flutter 앱]  <--위험 목록 / 제보------->  [서버 + DB]
```

| 구분      | 무엇인가                        | 하는 일                                                                |
|---------------|-------------------------------------|----------------------------------------------------------------------------|
| 서버 + DB     | FastAPI로 만든 서버와 데이터 저장소 | 단말·카메라·앱이 보낸 위험 정보를 저장하고, 앱이 요청하면 목록을 보내 준다 |
| 앱: 지도 화면 | 앱 첫 화면                          | 위험 지점을 지도에 아이콘으로 표시하고, 누르면 정보창을 보여 준다          |
| 앱: 제보 화면 | 사용자 직접 등록                    | 유형, 사진, 설명을 입력해 서버로 보낸다                                    |
| 앱: 주행 모드 | 자전거를 탈 때 켜는 모드            | 내 위치를 따라가며 앞쪽 위험에 가까워지면 음성·진동으로 알린다             |

## 3. 역할 분담

| 파트    | 담당 | 만드는 것                                                | 함께 맞출 사람                   |
|-------------|----------|--------------------------------------------------------------|--------------------------------------|
| 데이터·서버 | (이름)   | FastAPI 서버와 DB, 앱의 서버 통신 코드(data/), 오류 처리     | 단말 담당, 카메라 AI 담당            |
| 주행·알림   | (이름)   | 위치 추적, 앞쪽 위험 고르기, 음성·진동 알림, 주행 시뮬레이션 | 단말 담당 (GPS 기록 공유)            |
| 화면        | (이름)   | 지도 화면, 마커·정보창, 제보 화면, 앱 디자인                 | 카메라 AI 담당 (방학 중 카메라 화면) |

데이터·서버 파트가 **가장 먼저** 움직여야 한다. 하드웨어 팀이 12~13주차에 단말에서 서버로 보내는 시험을 하려면 서버가 먼저 있어야 하기 때문이다.

## 4. 하드웨어 팀과 협업할 지점

| 주차 | 하드웨어 팀 진행               | 소프트웨어가 해 줄 것 / 받을 것                                                                          |
|----------|------------------------------------|--------------------------------------------------------------------------------------------------------------|
| 12주차   | 부품 도착, SD 기록 코드            | **API 형식 확정**, 서버를 노트북에서 띄워 주소 공유 (단말이 보내기 시험을 할 수 있게)                        |
| 13주차   | 자전거 장착, 실제 주행 데이터 수집 | 단말이 보낸 충격이 서버 DB에 저장되는지 함께 확인. 하드웨어 팀의 주행 GPS 기록을 받아 주행 시뮬레이션에 사용 |
| 14주차   | 충격 감지 기준 조정                | 단말 → 서버 → 앱 지도에 점이 찍히는 것 함께 확인                                                         |
| 15주차   | 카메라 인식 결과 전송, 통합 시험   | 카메라 결과가 서버를 거쳐 지도에 뜨는 것 확인, 체험형 데모 함께 준비                                         |
| 16주차   | 성과 정리                          | API 문서, 시연 영상 함께 정리                                                                                |

#### 하드웨어 팀과 먼저 정할 것 (12주차 첫 회의)

1. **API 주소와 필드 이름:** 8장 초안을 보고 확정한다.

2. **시간 형식:** GPS 시간 기준으로 맞춘다. 예: 2026-11-20T14:03:11+09:00

3. **severity(충격 크기) 단위:** 단말이 어떤 숫자를 보낼지 정한다. 예: 최대 가속도(g)

4. **서버 위치:** 개발 중에는 노트북 + 스마트폰 핫스팟, 시연 때는 노트북 현장 실행인지 인터넷 서버인지 정한다.

## 5. 이번 학기 주차별 계획

### 11주차 남은 기간 (이번 주): 준비

| 담당    | 할 일                                                                                    |
|-------------|----------------------------------------------------------------------------------------------|
| 공통        | Flutter, Android Studio, VS Code, GitHub Desktop 설치. 각자 Flutter 기본 앱을 폰에 띄워 보기 |
| 데이터·서버 | Python, FastAPI 설치. 간단한 서버를 띄워 /docs 화면 열어 보기                                |
| 공통        | GitHub 저장소 만들기, 3명 초대                                                               |

**확인:** 3명 모두 자기 폰에서 Flutter 기본 앱이 켜진다.

### 12주차: 뼈대 만들기와 약속 정하기

**목표:** 앱 프로젝트와 서버의 기본 틀을 만들고, 하드웨어 팀이 쓸 서버를 열어 준다.

| 담당    | 할 일                                                                                                                |
|-------------|--------------------------------------------------------------------------------------------------------------------------|
| 데이터·서버 | 하드웨어 팀과 API 형식 확정 → FastAPI로 API 4개 만들기(받기·저장·조회) → 노트북에서 서버 실행, 같은 핫스팟에서 주소 공유 |
| 주행·알림   | 앱에서 내 위치(geolocator)를 받아 화면에 위도·경도·속도 표시. 밖에서 걸으며 값 확인                                      |
| 화면        | Flutter 프로젝트 생성, 폴더 구조 만들기, 지도(flutter_map)를 띄우고 가짜 위험 지점 3개를 마커로 표시                     |
| 공통        | 저장소에 팀 규칙 파일(CLAUDE.md) 작성: 폴더 구조, 담당자, API 형식, 사용 패키지                                          |

**하드웨어 협업:** 단말 담당이 노트북 서버 주소로 시험 데이터를 보내 볼 수 있게 한다.

**확인:** 서버 /docs 화면에서 데이터를 넣고 조회할 수 있다. 앱 지도에 가짜 마커 3개가 보인다.

### 13주차: 앱과 서버 연결하기

**목표:** 가짜 데이터를 지우고, 앱 지도가 서버의 위험 목록을 보여 준다.

| 담당    | 할 일                                                                                     |
|-------------|-----------------------------------------------------------------------------------------------|
| 데이터·서버 | 앱의 서버 통신 코드 작성: 위험 목록 받기(GET /hazards), 제보 보내기(POST /reports, 사진 포함) |
| 주행·알림   | 앞쪽 위험 고르기 로직(진행 방향 기준), 100m 앞 음성 예고(flutter_tts). 주행 시뮬레이션 만들기 |
| 화면        | 마커를 누르면 정보창, 제보 화면(유형 선택, 사진, 설명), 위험 유형별 아이콘·색                 |

**하드웨어 협업:** 단말이 보낸 충격 이벤트가 서버 DB에 저장되는지 함께 확인한다. 하드웨어 팀의 실제 주행 GPS 기록(CSV)을 받아 시뮬레이션 재생에 쓴다.

**확인:** 서버에 넣은 위험이 앱 지도에 뜬다. 앱에서 제보하면 서버에 저장된다. 시뮬레이션에서 위험 앞 100m에 음성이 나온다.

### 14주차: 단말 연동과 첫 실제 주행

**목표:** 단말 → 서버 → 지도 흐름을 완성하고, 실제 자전거로 알림을 시험한다.

| 담당    | 할 일                                                                                                            |
|-------------|----------------------------------------------------------------------------------------------------------------------|
| 데이터·서버 | 서버에서 충격 이벤트를 위험 지점으로 바꾸기(같은 위치 15m 안은 하나로 묶기). 앱 새로고침(30초마다), 인터넷 끊김 처리 |
| 주행·알림   | 도착 5초 전 진동·경고음, 같은 지점 5분 재알림 금지, 화면 켜짐 유지. 실제 자전거 주행 1차 시험                        |
| 화면        | "아직 있어요 / 없어졌어요" 버튼, 확정·미확인 표시(진하게·흐리게), 주행 모드 화면                                     |

**하드웨어 협업:** 단말을 단 자전거로 요철을 지나간 뒤, 앱 지도에 점이 새로 찍히는지 함께 확인한다. (이번 학기 최소 목표)

**확인:** 단말 충격이 1분 안에 지도에 뜬다. 실제 주행에서 위험 지점 앞에서 음성 알림이 울린다.

### 15주차: 카메라 연동과 통합 시험

**목표:** 카메라 인식 결과까지 지도에 표시하고, 전체 흐름을 시험한다.

| 담당    | 할 일                                                                          |
|-------------|------------------------------------------------------------------------------------|
| 데이터·서버 | 카메라 인식 결과 받기(POST /reports, 사진 포함) 서버 확인. 실패한 제보 다시 보내기 |
| 주행·알림   | 실제 주행 2차 시험, 알림 거리·방향 값 조정, 알림 기록(성공·실패) 남기기            |
| 화면        | 카메라로 등록된 위험 표시 구분(아이콘), 전체 디자인 다듬기                         |
| 공통        | 체험형 데모 준비: 시연 순서 정하기, 서버 실행 위치 확정                            |

**하드웨어 협업:** 카메라 AI 담당이 인식 결과를 서버로 보내고, 지도에 뜨는지 함께 확인한다. 전체 통합 주행 시험을 함께 한다.

**확인:** 단말 충격, 카메라 인식, 사용자 제보 세 가지가 모두 지도에 뜨고, 주행 중 알림이 울린다.

## 6. 일정이 밀릴 때 우선순위

시간이 부족하면 아래 순서대로만 완성해도 이번 학기 목표를 보여 줄 수 있다.

1. 서버 + 앱 지도에 서버 데이터 표시

2. 단말 충격 → 서버 → 지도에 점 표시

3. 주행 중 음성 알림

4. 사용자 제보

5. 카메라 결과 표시

## 7. 겨울방학 계획 (대략)

> **방학 목표**
> 이번 학기 프로토타입을 **실제로 쓸 수 있는 앱**으로 끌어올린다. 카메라 AI를 앱 안에 넣고, 화면이 꺼져도 알림이 오게 하며, 서버를 인터넷에 올려 어디서든 시연할 수 있게 한다.

| 시기 | 단계 | 주요 작업 |
|---|---|---|
| 12월 말 ~ 1월 초<br>(약 2주) | 1단계: 정리와 안정화 | 이번 학기 코드 정리, 남은 버그 수정<br>서버를 인터넷(클라우드)에 배포<br>화면이 꺼져도 위치 추적·알림(백그라운드) |
| 1월 중순 ~ 1월 말<br>(약 3주) | 2단계: 핵심 기능 추가 | 앱 안에 카메라 AI 탑재(TFLite), 스마트폰 FPS 측정<br>카메라 인식 → 앱 알림 → 서버 제보 흐름 완성<br>필터(확정만, 유형별) |
| 2월 초 ~ 2월 중순<br>(약 2주) | 3단계: 정확도 높이기 | 알림 기준 개선: 진행 방향 ±45도 → 앞쪽 거리·옆쪽 거리 기준<br>신뢰도 계산(충격·카메라·제보 합산), 오래된 위험 자동 만료<br>카메라 인식과 충격 감지 교차 확인 |
| 2월 말<br>(약 1~2주) | 4단계: 시험과 다음 학기 준비 | 실제 주행 시험 반복, 평가 지표 측정(알림 성공률, 오알림, 인식률, 위치 오차)<br>다음 학기 주차별 계획 작성 |

#### 방학 중 파트별 중점

| 파트    | 방학 중 중점 작업                                                            |
|-------------|----------------------------------------------------------------------------------|
| 데이터·서버 | 서버 클라우드 배포, 신뢰도 계산·만료 규칙, 데이터 백업, API 문서 최신화          |
| 주행·알림   | 백그라운드 위치·알림, 알림 기준 개선(앞쪽·옆쪽 거리), 필요 시 단말 블루투스 연결 |
| 화면        | 카메라 AI 화면(하드웨어 팀 카메라 담당과 함께), 필터 화면, 전체 디자인 정리      |

#### 방학 중 하드웨어 팀과 협업

- 하드웨어 팀의 **충격 감지 정밀 조정, 추가 클래스 학습, 장착 케이스 개선** 결과를 받아 앱·서버에 반영한다.

- 카메라 모델 파일(TFLite)과 인식 결과 형식은 1월 초까지 카메라 AI 담당과 확정한다.

- 2단계와 3단계 사이(1월 말), 4단계(2월 말)에 **전원 통합 주행 시험**을 한다.

#### 방학 진행 방식

- 주 1회 온라인 회의: 각자 만든 것을 화면 공유로 실행해 보여 준다.

- 각자 방학 일정(여행, 아르바이트 등)을 미리 공유하고, 빠지는 기간의 작업을 조정한다.

- 단계가 끝날 때마다 GitHub에 정리해 올리고, 동작 영상을 남긴다.

| POST /events                       | 단말               | 충격 이벤트 1건 저장            |
| POST /reports                      | 카메라 AI, 앱 제보 | 위험 제보 저장 (사진 포함)      |
| GET /hazards?lat=&lng=&radius=1000 | 앱                 | 주변 위험 지점 목록             |
| POST /hazards/{id}/votes           | 앱                 | "아직 있어요 / 없어졌어요" 응답 |

## 9. 협업 방식

- 코드는 GitHub 저장소 하나에서 관리하고, 각자 자기 폴더만 고친다.

- AI로 코드를 작성할 때는 CLAUDE.md(팀 규칙, API 형식)를 함께 붙여 넣는다.

- 기능 하나가 끝날 때마다 올리고, 다른 팀원이 실행해 본 뒤 합친다.

- 매주 1회 하드웨어 팀과 함께 서버를 켜고 전체 흐름을 실행해 본다.
