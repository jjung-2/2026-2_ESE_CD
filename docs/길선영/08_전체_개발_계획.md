# 전체 개발 계획 (하드웨어 + 소프트웨어)

노면 위험 감지 프로젝트 · 이번 학기(11~16주차) 및 겨울방학 계획 · 기준일 2026-11-15

> 참고: 이 문서의 API 초안(필드 이름 `lng`, `timestamp` 등)은 계획 당시 초안이다. 현재 팀 기준은 저장소의 [`docs/api.md`](../api.md)이며, 필드 이름은 `lon`, `time`, `event_id`로 확정되었다.

## 1. 프로젝트 개요와 이번 학기 목표

자전거에 장착한 단말(IMU·GPS)과 스마트폰 카메라(2D)로 노면 위험을 감지하고, 서버에 모아 앱 지도에 표시하며, 주행 중 위험 지점에 가까워지면 이용자에게 알리는 플랫폼을 개발한다.

> **이번 학기 목표 (16주차까지)**
> 단말이 감지한 충격과 카메라가 인식한 위험이 서버에 저장되고, 앱 지도에 표시되며, 실제 주행 중 위험 지점에 가까워지면 음성으로 알리는 **1차 프로토타입**을 완성한다.

#### 최소 목표 (일정이 부족할 때 가장 먼저 완성할 흐름)

1. 서버의 위험 지점이 앱 지도에 표시된다.

2. 단말 충격 → 서버 → 앱 지도에 점이 찍힌다.

3. 실제 주행 중 위험 지점에 가까워지면 음성으로 알린다.

4. 카메라 인식 결과가 서버를 거쳐 지도에 표시된다.

## 4. 전체 구조와 데이터 흐름

```text
[단말 ESP32] ---충격 이벤트(와이파이)---> [서버 + DB]
[카메라 AI] ---인식 결과--------------> [서버 + DB]
[Flutter 앱] <--위험 목록 / 제보-------> [서버 + DB]
```

| 보내는 쪽 | API                  | 받는 쪽 | 내용                                   |
|---------------|--------------------------|-------------|--------------------------------------------|
| 단말 (ESP32)  | POST /events             | 서버        | 충격 이벤트 (위치·시간·충격 크기)          |
| 카메라 AI     | POST /reports            | 서버        | 인식한 위험 요소 제보 (사진 포함)          |
| 앱            | POST /reports            | 서버        | 사용자 직접 제보 (유형·사진·설명)          |
| 앱            | GET /hazards             | 서버        | 주변 위험 지점 목록 조회, 지도 표시와 알림 |
| 앱            | POST /hazards/{id}/votes | 서버        | "아직 있어요 / 없어졌어요" 응답            |

#### 단말 연결 방식

- 단말은 와이파이로 서버에 직접 HTTP POST를 보낸다. 주행 중에는 스마트폰 핫스팟에 연결한다.

- 개발 중에는 같은 핫스팟(또는 와이파이)에 서버를 켠 노트북을 두고, 그 노트북의 IP 주소로 보낸다.

- 이번 학기에는 앱과 단말을 블루투스로 직접 연결하지 않는다.

## 5. 데이터 기록 방식: 사후 라벨링

> **★ 12주차 변경 사항**
> 주행 중에는 센서 값(시간·가속도·자이로·GPS)을 계속 기록하고, 주행이 끝난 뒤 데이터와 영상을 보며 충격 구간에 라벨을 붙인다(사후 라벨링).
> 택트 스위치는 기본 방식이 아니라 대안으로만 준비한다.

- **장점:** 주행 중 버튼을 누를 필요가 없어 안전하고, 기록 코드가 단순하다.

- **주의:** 센서 기록과 카메라 영상의 시간이 맞아야 하므로 모든 기록에 시간을 넣는다. GPS 시간을 기준으로 맞춘다.

- **대안:** 사후 라벨링이 어려우면 택트 스위치로 주행 중 충격 순간을 직접 표시한다.

| HW 단말        | 동작 영상·주행 데이터 보관, 방학 작업 목록 정리 |
| HW 카메라 AI   | 학습 데이터·모델 버전 정리                      |
| SW 데이터·서버 | API 문서 정리(주소, 필드, 예시)                 |
| SW 주행·알림   | 알림 성공률, 오알림 횟수 정리                   |
| SW 화면        | 앱 화면 캡처, 시연 영상 촬영                    |

**함께 확인:** 이번 학기 성과를 정리하고 방학 계획을 확정한다.

## 7. 두 팀이 먼저 정할 것 (12주차 첫 회의)

1. **API 주소와 필드 이름:** 9장 초안을 보고 확정한다. 이 형식이 어긋나면 마지막에 전부 고쳐야 하므로 가장 먼저 정한다.

2. **시간 형식:** GPS 시간 기준. 예: 2026-11-20T14:03:11+09:00 (라벨링과 영상 맞추기에도 사용)

3. **severity(충격 크기) 단위:** 단말이 보낼 숫자를 정한다. 예: 최대 가속도(g)

4. **서버 위치:** 개발 중에는 노트북 + 스마트폰 핫스팟, 시연 때는 노트북 현장 실행 또는 인터넷 서버 중 선택

5. **주행 데이터 공유 방식:** 하드웨어 팀의 GPS·센서 기록 CSV를 공유 폴더에 올려 소프트웨어 시뮬레이션에 사용

## 8. 겨울방학 계획 (대략)

> **방학 목표**
> 이번 학기 프로토타입을 **실제로 쓸 수 있는 수준**으로 끌어올린다. 충격 감지와 카메라 인식의 정확도를 높이고, 카메라 AI를 앱 안에 넣으며, 서버를 인터넷에 올려 어디서든 시연할 수 있게 한다.

| 시기 | 단계 | 하드웨어 팀 | 소프트웨어 팀 |
|---|---|---|---|
| 12월 말 ~ 1월 초<br>(약 2주) | 1단계<br>정리와 안정화 | 이번 학기 데이터 정리, 장착 케이스 개선 설계 | 코드 정리·버그 수정, 서버 클라우드 배포, 화면이 꺼져도 알림(백그라운드) |
| 1월 중순 ~ 1월 말<br>(약 3주) | 2단계<br>핵심 기능 추가 | 추가 클래스 정확도 높이기, 카메라 모델 스마트폰용 변환(TFLite) | 앱 안에 카메라 AI 탑재, 카메라 인식 → 앱 알림 → 서버 제보, 필터(확정만, 유형별) |
| 2월 초 ~ 2월 중순<br>(약 2주) | 3단계<br>정확도 높이기 | 충격 감지 정밀 조정, 장착 케이스 제작 | 알림 기준 개선(앞쪽·옆쪽 거리), 신뢰도 계산, 오래된 위험 자동 만료, 카메라·충격 교차 확인 |
| 2월 말<br>(약 1~2주) | 4단계<br>시험과 준비 | 반복 주행으로 감지 성능 측정 | 알림 성공률·오알림·위치 오차 측정, 다음 학기 계획 작성 |

#### 방학 중 협업

- 카메라 모델 파일(TFLite)과 인식 결과 형식은 1월 초까지 카메라 AI 담당과 화면 담당이 확정한다.

- 2단계가 끝나는 1월 말과 4단계인 2월 말에 **전원 통합 주행 시험**을 한다.

- 주 1회 온라인 회의에서 각자 만든 것을 화면 공유로 실행해 보여 준다.

- 각자 방학 일정(여행, 아르바이트 등)을 미리 공유하고, 빠지는 기간의 작업을 조정한다.

## 9. API 초안 (두 팀이 확정할 것)

| 주소                           | 보내는 쪽 | 하는 일                     |
|------------------------------------|---------------|---------------------------------|
| POST /events                       | 단말          | 충격 이벤트 1건 저장            |
| POST /reports                      | 카메라 AI, 앱 | 위험 제보 저장 (사진 포함)      |
| GET /hazards?lat=&lng=&radius=1000 | 앱            | 주변 위험 지점 목록             |
| POST /hazards/{id}/votes           | 앱            | "아직 있어요 / 없어졌어요" 응답 |

단말이 보내는 데이터 예시

```json
{
"source": "imu",
"type": "bump",
"lat": 37.3891,
"lng": 126.6432,
"timestamp": "2026-11-20T14:03:11+09:00",
"severity": 2.4,
"device_id": "bike-01"
}
```

앱이 받는 위험 지점 예시

```json
{
"id": 12,
"type": "pothole",
"lat": 37.3893,
"lng": 126.6447,
"severity": 2,
"status": "confirmed",
"report_count": 4,
"updated_at": "2026-11-20T14:05:00+09:00"
}
```

## 10. 일정 리스크와 대안

| 리스크                     | 대안                                                                                       |
|--------------------------------|------------------------------------------------------------------------------------------------|
| 부품 배송이 12주차를 넘김      | microSD 저장은 뒤로 미루고, 센서 원본 값을 와이파이로 서버에 보내 저장한다.                    |
| 서버 준비 지연                 | 하드웨어 팀은 FastAPI /docs로, 앱은 가짜 데이터로 계속 개발하고 서버가 준비되면 주소만 바꾼다. |
| 사후 라벨링이 어려움           | 택트 스위치로 주행 중 충격 순간을 직접 표시한다.                                               |
| 스마트폰 카메라 처리 속도 부족 | 입력 크기를 줄이거나 더 작은 모델을 쓰고, 이번 학기는 인식 동작 확인까지를 목표로 한다.        |
| 실제 주행 시험 지연            | 하드웨어 팀의 주행 기록으로 시뮬레이션을 돌려 로직을 먼저 검증한다.                            |
| 전체 일정 부족                 | 1장의 최소 목표(지도 표시 → 단말 연동 → 음성 알림 → 카메라 표시) 순서로 완성한다.              |

## 11. 협업 방식

- 코드는 GitHub 저장소 하나에서 관리하고, 각자 자기 폴더만 고친다.

- AI로 코드를 작성할 때는 팀 규칙 파일(CLAUDE.md)을 함께 제공한다.

- 기능 하나가 끝날 때마다 올리고, 다른 팀원이 실행해 본 뒤 합친다.

- 매주 1회 두 팀이 모여 서버를 켜고 전체 흐름을 실행해 본다.
