# BikeMap 자료조사 및 기술 검토 기록

> **프로젝트** | 실시간 자전거 위험 요소 감지·경고 및 공유 플랫폼 (BikeMap)  
> **자료조사 기간** | 2026.10.24. ~ 2026.11.15.  
> **정리 분야** | 서비스 기획 · 컴퓨터비전 · 센서/GPS · 모바일 앱 · 시스템 연동 · 데이터 수집  
> **후속 개발 기록** | 2026.11.18. (문서 마지막에 별도 정리)

## 1. 프로젝트 개요 및 조사 방향

BikeMap은 자전거 이용자가 주행 중 만날 수 있는 위험 요소를 감지하고, 해당 위치를 지도에 표시하여 다른 이용자에게도 경고하는 서비스다. 일반적인 자전거 지도에서 제공하는 위치 확인·경로 안내에 **주행 환경 감지, 위험 위치 누적, 접근 알림, 이용자 간 공유**를 결합하는 방향으로 기술 검토를 진행했다.

초기 대상은 자전거이며, 위험 요소는 포트홀을 중심으로 노면 단차와 장애물 등으로 분류한다. 앱에서 위험 지점을 조회하고 사용자 제보를 반영하는 기능을 기본으로 두며, IMU와 GPS를 활용한 위험 후보 자동 등록, 스마트폰 카메라의 포트홀 인식을 함께 다룬다.

### 핵심 기능 구성

| 기능 | 주요 내용 |
| --- | --- |
| 노면 충격 감지 | IMU로 비정상적인 진동·충격을 감지하여 위험 후보 생성 |
| 위치 기반 등록 | 감지 시점의 GPS 좌표를 위험 정보에 연결 |
| 위험 지도 | 위치·종류·상태를 마커로 표시하고 상세 정보 제공 |
| 접근 경고 | 저장된 위험 지점에 접근하는 이용자에게 알림 |
| 정보 정정 | 잘못 등록된 위험에 대한 확인·삭제 요청 |
| 영상 기반 인식 | 스마트폰 카메라로 전방 포트홀을 인식하고 위험 경고와 연결 |
| 그룹 공유 | 한 이용자가 탐지한 위험 정보를 함께 주행하는 이용자에게 전달 |

이 기능을 기준으로 **감지 장치 / 영상 인식 / 서버 / 모바일 앱 / 지도·경고** 사이에서 어떤 데이터를 주고받아야 하는지 조사했다.

## 2. 기존 자전거 지도 서비스와의 차별화

### 2.1 일반 지도 기능과 위험 감지 서비스 구분

기존 지도 서비스에서 중심이 되는 기능은 경로 탐색과 현재 위치 표시다. BikeMap에서는 같은 지도 위에 **도로 상태와 주행 위험 정보를 기록한다는 점**을 차별 요소로 잡았다.

| 비교 항목 | 일반 지도 중심 기능 | BikeMap에서 강조한 기능 |
| --- | --- | --- |
| 지도 활용 | 경로와 현재 위치 확인 | 위험 지점과 현재 위치를 함께 확인 |
| 위험 정보 | 지도에 포함된 정적인 정보 조회 | 센서·카메라·이용자 제보를 통한 정보 축적 |
| 주행 중 안내 | 길 안내 중심 | 위험 지점 접근 및 신규 위험 감지 시 경고 |
| 이용자 참여 | 위치 검색·경로 공유 | 위험 제보, 확인 및 삭제 요청 |
| 단체 주행 | 구성원별 개별 지도 사용 | 위험 감지 내용을 다른 라이더에게 공유 |

### 2.2 위험 정보의 두 가지 유입 경로

위험 정보를 **이미 지도에 등록된 위험**과 **주행 중 새로 발견한 위험**으로 구분했다.

1. **기존 위험 접근 경고**: 앱이 GPS 현재 위치를 확인하고, 지도에 등록된 위험 지점과의 거리를 비교한 뒤 접근 알림을 제공한다.
2. **신규 위험 감지**: 스마트폰 영상 또는 IMU 충격 기록으로 위험 후보를 만들고, 위치와 함께 저장·공유한다.

이렇게 구분하면 전방 카메라가 항상 켜져 있지 않더라도 저장된 위험 위치에 대한 경고 기능을 구성할 수 있으며, 새로 발견한 위험은 다른 사용자의 이후 주행에 활용할 수 있다.

## 3. 스마트폰 카메라 기반 포트홀 인식

### 3.1 스마트폰을 사용하는 이유

별도의 Depth 카메라를 모든 자전거에 설치하는 방식은 장비 비용과 장착·운용 부담이 크다. 따라서 **일반 스마트폰 카메라로도 포트홀을 인식하는 방향**을 조사했다.

영상 인식 기능은 먼저 **포트홀 한 종류를 안정적으로 구분하는 것**에 초점을 맞추고, 탐지 결과를 주행 중 화면·음성 경고와 연결하도록 구성했다.

### 3.2 YOLO 기반 인식 방식 비교

| 항목 | 객체 탐지(Detection) | 세그멘테이션(Segmentation) |
| --- | --- | --- |
| 출력 | 포트홀을 둘러싼 바운딩 박스 | 포트홀의 픽셀 영역 |
| 활용 | 위험 존재 여부와 화면 내 대략적인 위치 확인 | 위험 영역의 모양·면적 분석 |
| 모바일 처리 | 비교적 단순한 결과 처리 | 마스크 후처리 및 추가 연산 고려 |
| 초기 검증 | 포트홀 탐지·경고 흐름 검증에 적합 | 위험 영역을 더 정밀하게 다룰 때 활용 |

초기 검토에서는 경량 YOLO 모델과 객체 탐지 방식으로 **인식 → 경고 → 위치 등록** 흐름을 먼저 구성하고, 필요에 따라 세그멘테이션을 적용하는 구조를 살폈다.

### 3.3 실시간 처리와 경고 지연

카메라에서 영상을 받는 속도와 모델이 프레임을 분석하는 속도는 다를 수 있다. 따라서 모든 프레임을 처리하는 것보다 **분석 해상도 조절, 일부 프레임 선택, 경량 모델 활용**으로 경고 반응 시간을 관리하는 방법을 검토했다.

```text
스마트폰 카메라
    ↓
영상 프레임 입력
    ↓
YOLO 포트홀 인식
    ↓
위험 위치·인식 결과 판단
    ├─ 주행자에게 화면·음성 경고
    └─ GPS 위치와 연결하여 위험 후보 생성
```

카메라에서 포트홀이 보인다고 해서 무조건 즉시 경고하면 멀리 있는 포트홀이나 주행 경로 밖에 있는 포트홀에도 경고할 수 있다. 그래서 **포트홀 인식 자체**와 **언제 경고할지 결정하는 로직**을 구분하여 조사했다.

### 3.4 영상 데이터 준비

공개 포트홀 데이터셋과 기존 YOLO 인식 사례를 검토하는 동시에, 실제 자전거 주행 시점에서 촬영한 데이터를 별도로 확보하는 방향을 정리했다.

- 스마트폰을 자전거에 고정하여 실제 도로 영상을 촬영한다.
- 포트홀에 바운딩 박스를 지정하여 학습·평가용 라벨을 만든다.
- 그림자, 균열, 맨홀, 물웅덩이 등 포트홀과 혼동하기 쉬운 장면도 포함한다.
- 카메라 높이와 촬영 각도를 일정하게 유지해 영상 조건을 비교하기 쉽게 만든다.
- 탐지 성능은 재현율·오탐 사례·추론 속도 등으로 평가하는 방식을 검토한다.

## 4. Depth 정보와 2D 영상 활용 방식

### 4.1 Depth 카메라와 일반 RGB 카메라 비교

Depth 카메라는 영상의 각 위치에 해당하는 깊이 정보를 얻는 데 활용할 수 있다. 반면 일반 스마트폰의 RGB 카메라는 **이미지 내 물체의 위치와 형태**를 직접 인식하는 데 적합하지만, 한 장의 영상만으로 실제 거리가 자동으로 계산되지는 않는다.

| 구분 | Depth 기반 접근 | RGB 카메라 기반 접근 |
| --- | --- | --- |
| 입력 정보 | 영상 및 거리·깊이 정보 | 2D 영상 |
| 주요 활용 | 위험 지점 거리·형상 분석 | 포트홀 시각적 인식 |
| 장비 구성 | 별도 카메라 또는 깊이 센서 | 일반 스마트폰 카메라 |
| 구현 시 고려 | 센서 비용·장착·캘리브레이션 | 카메라 자세·거리 추정·인식 정확도 |

### 4.2 2D 영상에서 주행 거리와 연결하기

일반 카메라로 감지한 포트홀을 실제 주행 거리와 연결하려면 **카메라의 장착 높이·각도·초점 특성, 도로면의 기하 관계**를 고려해야 한다.

검토한 방식은 다음과 같다.

- 카메라 보정으로 렌즈 왜곡과 내부 파라미터를 확인한다.
- 도로면을 기준으로 영상의 관심 영역(ROI)을 정한다.
- 카메라와 도로면의 관계를 이용한 투영 변환(Homography) 또는 실측 기준점을 검토한다.
- 영상 인식 결과를 주행 방향과 위험 지점 판단에 연결한다.

이 과정에서 **포트홀의 존재를 인식하는 작업**과 **몇 m 앞에 있는지 추정하는 작업**을 분리하여 설계했다. 정밀 거리 계산을 전제로 하지 않는 초기 경고 문구도 함께 검토했다.

## 5. IMU·GPS 기반 위험 후보 감지 및 하드웨어 구성

### 5.1 역할별 부품 조사

자전거에 부착할 소형 장치는 충격을 감지하고 해당 시점의 위치를 기록하는 역할을 맡는다.

| 구성 요소 | 조사한 부품·기술 | 역할 |
| --- | --- | --- |
| 마이크로컨트롤러 | ESP32 계열 / ESP32-S3 | 센서 데이터 수집과 통신 처리 |
| 관성 센서 | ICM-42688P 계열 IMU | 가속도·각속도 변화 측정 |
| GPS | SAM-M10Q 계열 모듈 | 감지 위치의 위도·경도 기록 |
| 로컬 저장 | microSD 모듈·카드 | 주행 로그 및 센서 데이터 저장 |
| 배선·조립 | 핀헤더, USB 케이블, 브레드보드, 점퍼선 | 장치 연결과 초기 동작 검증 |
| 장착 구조 | 스마트폰 거치대, 케이블타이, 벨크로 | 주행 중 카메라·센서 위치 고정 |

구매 전에는 센서의 전압·통신 방식, 배선 방식, 모듈 규격과 추가 부품 구성을 함께 비교했다. ESP32와 IMU, GPS가 각각 수행할 기능을 구분해 장치 구조를 정리했다.

### 5.2 충격 탐지와 위치 기록의 연결

```text
자전거 주행
    ↓
IMU 가속도·각속도 측정
    ↓
비정상 충격·진동 후보 판단
    ↓
감지 시점의 GPS 정보 연결
    ↓
위험 후보 데이터 생성
    ↓
서버 저장 → 지도 표시 및 사용자 경고
```

도로의 모든 진동이 포트홀을 뜻하는 것은 아니므로, **일상적인 노면 진동과 큰 충격을 구분하는 기준**을 검토했다. 스마트폰 카메라가 인식한 결과와 충격 기록을 비교하는 방식도 오탐을 줄이기 위한 방안으로 정리했다.

### 5.3 추가 하드웨어 검토

센서 장치의 개발 범위를 확장하는 방법으로 두 개의 IMU를 이용한 측정값 비교, 주행 속도 측정을 위한 바퀴 센서, 저장 로그 기반 분석, 경고 명령을 진동으로 전달하는 장치 구성도 검토했다.

이 중 **핸들바 진동 경고**는 스마트폰의 위험 인식 결과를 BLE로 ESP32에 전달하고, ESP32가 진동 모터를 제어하는 구조로 정리했다.

```text
스마트폰 위험 감지
    ↓
BLE 경고 명령
    ↓
ESP32
    ↓
모터 구동회로
    ↓
핸들바 진동 알림
```

장치 구성뿐 아니라 경고 명령부터 진동 발생까지의 지연 시간을 측정하는 방법도 함께 검토했다.

## 6. 반응형 웹과 모바일 앱 비교

처음에는 웹 지도 중심으로 서비스를 구성하는 방법과 모바일 앱으로 개발하는 방법을 비교했다.

| 항목 | 반응형 웹 | 모바일 앱 |
| --- | --- | --- |
| 접속 방식 | 브라우저에서 바로 사용 | 앱 설치 후 실행 |
| 지도·제보 | 구현 가능 | 구현 가능 |
| GPS 활용 | 브라우저 권한 및 실행 조건의 영향 | 모바일 위치 권한·서비스 활용 |
| 카메라 분석 | 브라우저 환경 제약 고려 | 카메라 프레임 분석과 기능 연동에 유리 |
| 센서 연동 | 기기·브라우저별 지원 차이 | BLE 등 모바일 기능 통합에 유리 |
| 경고 방식 | 화면 중심, 실행 환경 영향 | 음성·진동·알림 기능과 연동 가능 |

카메라, GPS, 경고, 그룹 주행 기능이 하나의 서비스 안에서 동작해야 한다는 점을 고려해 **모바일 앱 중심 구조**를 채택했다. 이후 실제 앱 개발에서는 Flutter를 사용하여 지도 화면을 구성했다.

## 7. 앱·서버·센서 연동 구조

### 7.1 데이터 흐름

프로젝트 기능을 세 부분으로 나누어 정리했다.

- **현장 감지:** 스마트폰 카메라와 자전거 부착 IMU/GPS에서 위험 후보 정보 생성
- **서버 처리:** 위험 유형·위치·시각·확인 상태를 저장하고 이용자에게 전달
- **앱 화면:** 현재 위치와 위험 마커 표시, 접근 경고, 상세 정보 및 제보 기능 제공

```text
[스마트폰 카메라] ── 포트홀 인식 ──┐
                                ├── 위험 후보 ── [서버 / 위험 DB]
[IMU + GPS 장치] ── 충격·위치 ───┘                     │
                                                     ├── 지도 위험 마커
                                                     ├── 사용자 접근 경고
                                                     ├── 제보·확인·삭제 요청
                                                     └── 그룹 주행 위험 공유
```

실시간 공유 구조에서는 서버가 새 위험 정보를 받은 뒤 연결된 사용자에게 전달하는 방법을 검토했다. 이와 관련하여 WebSocket 기반 이벤트 전달 방식과 지도 데이터를 제공하는 API의 역할을 구분했다.

### 7.2 위험 지점 데이터 항목

| 데이터 | 사용 목적 |
| --- | --- |
| 위험 ID | 지점을 구분하기 위한 고유 식별자 |
| 위험 종류 | 포트홀·노면 단차·장애물 등의 분류 |
| 위도·경도 | 지도 마커 표시와 접근 거리 계산 |
| 감지 시각 | 감지 이력 및 정보 관리 |
| 감지 경로 | 카메라·IMU·사용자 제보 구분 |
| 위험 설명 | 이용자에게 세부 정보 제공 |
| 확인 상태 | 확인·정정 및 삭제 요청 처리 |

### 7.3 접근 경고와 그룹 공유

기존 위험 지점과 현재 위치의 거리를 계산해 사용자가 위험에 가까워질 때 알림을 표시하는 구조를 정리했다. 단체 주행에서는 앞선 이용자가 감지한 위험을 같은 그룹 사용자에게 전달하여, 뒤따르는 이용자도 미리 확인할 수 있도록 흐름을 구성했다.

## 8. 위험 지도와 UI 구성

위험 정보는 지도 마커와 상세 정보창으로 확인하도록 구성했다. 발표용 시연 흐름과 모바일 앱 구조를 함께 고려하여 화면 역할을 분리했다.

| 화면 | 표시 정보 | 주요 동작 |
| --- | --- | --- |
| 메인 지도 | 현재 위치, 위험 마커, 가까운 위험 | 마커 선택, 주행 시작, 그룹 메뉴 |
| 주행 화면 | 카메라 영상, 인식된 위험, 경고 표시 | 전방 위험 알림, 주행 정보 확인 |
| 위험 상세 | 종류, 설명, 위치, 확인 상태 | 위험 정보 확인 및 정정 요청 |
| 그룹 주행 | 그룹원 위치와 공유 위험 | 새 위험 알림 수신 및 공유 |

지도에서는 포트홀·노면 단차·장애물을 서로 다른 색상의 마커로 구분하고, 마커를 누르면 위험 상세 정보가 나타나도록 설계했다. 실제로 감지된 위험과 기존에 저장된 위험은 데이터 처리 경로를 구분해 앱에서 표시한다.

## 9. 주행 데이터 수집 및 작업 분담

### 9.1 실험 데이터 수집 체계

카메라 인식과 IMU 충격 탐지 결과를 실제 도로 주행 조건에 맞춰 검증하기 위한 데이터 수집 단계를 정리했다.

1. 자전거에 카메라와 센서 장치를 안정적으로 고정한다.
2. 주행 영상과 IMU·GPS 데이터를 기록한다.
3. 영상에서 포트홀 위치를 확인하고 라벨링한다.
4. 영상 감지 결과와 충격 기록을 비교한다.
5. 오탐 사례를 구분하고 인식·경고 로직 개선에 활용한다.

영상만 확보하는 것이 아니라 **위치·감지 시각·센서 측정값**을 함께 관리하는 것이 중요하다고 보았다. 캠퍼스 및 주변 도로를 우선 대상으로 검토했고, 수집 환경과 카메라 거치 조건을 함께 정리했다.

### 9.2 기능별 역할 분리

개발을 한 사람이 순서대로 진행하는 구조보다, 서로 의존하는 데이터 형식을 먼저 정하고 기능별로 병렬 작업하는 방식을 검토했다.

| 담당 영역 | 작업 내용 |
| --- | --- |
| 임베디드 | ESP32, IMU, GPS 측정과 데이터 기록 |
| 영상 인식 | 카메라 데이터·포트홀 탐지·라벨링 |
| 서버 | 위험 정보 저장, API, 실시간 전달 |
| 모바일 앱 | 지도, 현재 위치, 위험 상세 화면 |
| 경고·통합 | 접근 판단, 알림, 그룹 공유 및 모듈 연동 |

센서 데이터와 서버 API의 입력·출력 형식을 맞추면 영상 인식이나 하드웨어가 완성되기 전에도 **가상 위험 데이터로 앱 기능을 먼저 검증**할 수 있다. 이에 따라 지도 화면 개발과 실제 위험 탐지 기능을 분리하는 방식을 정리했다.

## 11. 기술 검토 정리

이번 조사에서 가장 중요한 방향은 **위험 정보를 감지하는 기술과 위험을 전달하는 서비스를 분리하면서도 하나의 흐름으로 연결하는 것**이었다.

- 지도에 이미 저장된 위험은 **GPS 접근 경고**로 안내한다.
- 처음 발견한 위험은 **카메라 또는 IMU 측정 결과**를 바탕으로 후보를 생성한다.
- 새 위험은 **위치 정보와 함께 저장**해 다른 이용자도 활용할 수 있도록 한다.
- 잘못된 위험 정보는 **사용자의 확인 및 삭제 요청**을 통해 관리한다.
- 단체 주행에서는 **위험 정보를 실시간으로 공유**하여 후방 이용자에게 전달한다.
- 앱 개발은 실제 장치와 서버가 없어도 **테스트 데이터로 지도·상세 정보 화면을 먼저 구현**할 수 있도록 구성한다.
